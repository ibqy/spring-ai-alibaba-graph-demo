# 先建立 Graph 的心智模型

## 它解决什么问题

普通 ChatClient 调用解决“输入提示词，拿到回答”。当一个任务还需要分支判断、并发校验、等待人工审批、重试或恢复时，仅靠一条长提示词不足以表达控制流程。

Graph 把控制流程留在 Java 程序里，把适合语言模型的步骤放进模型节点。模型可以写草稿，却不应该通过生成一句“我已同意”获得审批权限。

```text
业务输入 -> 状态 -> 节点处理 -> 状态增量 -> 边选择下一步
                         ^                 |
                         +---- 有界循环 ---+
```

本项目使用 Spring AI Alibaba 的原生 `StateGraph`，不是用自建状态机模拟 Graph，也不是给 ChatClient 增加一个 Agent 名字。

## 六个基础对象

| 对象 | 含义 | 本项目中的例子 |
| --- | --- | --- |
| `StateGraph` | 尚未执行的图定义 | 工单图包含分类、检索、起草、审核、结案节点 |
| `OverAllState` | 当前执行可读取的共享状态 | `message`、检索资料、草稿、审批结论 |
| `KeyStrategyFactory` | 为状态键指定更新方式 | 结果替换，轨迹追加 |
| Node | 接收状态并返回更新的动作 | 校验一张报销单 |
| Edge | 决定下一个节点的控制关系 | 验证通过到审核，失败到拒绝 |
| `CompiledGraph` | 经过校验、可执行的图 | 同步调用、节点事件流、检查点恢复 |

`graph()` 定义图；`compile()` 验证结构并设置执行选项；`invoke()` 或 `stream()` 才真正执行。查看 Mermaid 图不会运行模型或产生业务副作用。

## 状态更新是“增量”，不是整个状态

节点应当返回自己产生的字段。它不需要复制全部输入，也不应直接修改其他节点的容器。

```java
state -> Map.of("approved", true)
```

这表示更新一个键，而不是把其余字段删除。对追加策略尤其要注意：返回新增条目，不要把已有列表重新返回，否则旧条目会再次追加。

| 策略 | 适合的数据 | 常见错误 |
| --- | --- | --- |
| Replace | 当前结果、计数、决策 | 多个并行分支覆盖同一键，丢失结果 |
| Append | 轨迹、证据片段集合 | 返回完整历史导致重复 |

详情见 [03 状态合并](/lessons/03-state)。

## 控制流和数据流不是一回事

一条边表示执行顺序，不表示“只把上个节点的返回值传给下个节点”。节点读取的是合并后的状态。因此必须明确哪些键是用户输入、哪些是程序产生、哪些只允许人工审批写入。

统一运行接口只接受课程公开的 `sampleInput` 字段。内部字段如 `approved` 不能通过初始输入注入，而是由独立恢复接口写入。

## 分支、循环与并行

- **条件分支**：路由函数输出逻辑标签，再映射到具体节点。标签没有对应边会导致执行失败。
- **循环**：回边使某段图再次执行；必须定义业务停止条件，并设置框架执行上限作为最后一道保护。
- **并行**：多个分支产生独立结果，汇聚节点依赖全部必要结果；别假定返回顺序稳定。
- **子图**：把局部流程作为父图的节点，重点是输入输出键的约定，而不是无限嵌套。

`node_async` 是同步动作的适配器，名字里有 async 并不意味着动作自动切换到另一个线程。本项目的并行课程会区分图分支结构和实际异步执行，并用测试验证汇聚。

## 检查点与会话记忆不同

对话记忆通常保存消息列表，目的是让模型知道此前聊了什么。Graph 检查点保存图执行状态与下一步位置，目的是继续流程。

`threadId` 标识一次逻辑执行。恢复必须使用原来的图、Saver 和会话标识；新建一份空 MemorySaver 后传入同一个字符串，并不能找回原有状态。

**1.1.2.2 的一个重要细节**：普通节点更新允许未声明键按 Replace 合并，但恢复时 `OverAllState.input()` 只装载已经注册策略的键。因此必须在 `KeyStrategyFactory` 中明确声明所有需要跨中断保留的字段，尤其是草稿、业务编号和 `approved`。不能因为未中断时运行成功，就省略这些声明。

本项目的 `MemorySaver` 只存在于当前 JVM。**检查点可恢复不等于进程重启后可恢复**，后者需要持久化存储、序列化兼容和副作用幂等共同保证。

详情见 [08 检查点](/lessons/08-checkpoint)、[09 会话隔离](/lessons/09-isolation)。

## 人工介入的正确顺序

```text
准备草稿 -> 在 review 前中断 -> 返回 executionId
                                  |
                      人工提交 approved=true/false
                                  |
                更新原检查点 -> withResume -> 按边继续
```

HTTP 请求结束不是流程结束。服务返回 `WAITING_REVIEW` 时，业务副作用尚未发生。批准与拒绝必须是不同分支，模型输出不能替代这个决定。

## 流式输出的两个层次

1. **节点事件流**：每完成一个图节点，返回该节点名称与状态。本项目公共 SSE 接口演示这一层。
2. **模型 token 流**：模型生成过程中持续输出文本片段，需要流式模型调用与对应输出适配。

看到 SSE 逐条输出并不代表实现了 token 级打字机效果。两者的粒度、错误处理和客户端展示方式不同。

## Graph、ReactAgent 与工作流引擎

| 工具 | 适合的问题 | 本项目的定位 |
| --- | --- | --- |
| ChatClient | 单次或多轮模型交互 | 模型调用可以成为图中一步 |
| ReactAgent | 模型驱动的工具选择与推理循环 | 不用它替代本课程对图结构的讲解 |
| StateGraph | 显式控制状态、边、并发和中断 | 本项目的主线 |
| 完整业务工作流平台 | 身份权限、长期任务、审计、运维治理 | 本项目没有冒充提供这些能力 |

学习顺序是先理解控制流，再接模型，最后处理业务一致性。先跑 [第一张图](/lessons/01-hello)，再逐个增加复杂度。
